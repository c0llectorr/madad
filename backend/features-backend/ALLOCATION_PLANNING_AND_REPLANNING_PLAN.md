# Feature Plan: Resource Allocation Planning & Dynamic Replanning
**File:** `features-backend/ALLOCATION_PLANNING_AND_REPLANNING_PLAN.md`
**Module:** `app.api.routes.plan`, `app.services.prioritization`, `app.services.replanning`, `app.schemas.plan`
**Primary Endpoints:** `POST /api/plan/generate`, `POST /api/plan/replan`

---

## 1. Feature Overview & Functional Objective
Solves the constrained disaster relief matching problem. Ranks unserved sites by priority score, matches site demand against available depot inventories, and produces an explainable, ranked allocation plan. When field situations change (e.g. newly reported urgent medical needs, road collapse, or completed deliveries), the dynamic replanning engine re-evaluates unstarted sites, computes rank and route deltas, and presents a targeted diff without disrupting en-route convoys.

---

## 2. SOLID Architectural Mapping

- **Single Responsibility Principle (SRP):**
  - `services/prioritization.py`: Calculates site priority ranking and reasoning strings.
  - `services/replanning.py`: Computes delta comparisons between previous plan state and recomputed state.
  - `routes/plan.py`: Handles allocation generation requests, triggers replanning, and enforces resource array contracts.
  - `schemas/plan.py`: Strict Pydantic models for allocation requests, itemized resource lists, and replan diff responses.
- **Open/Closed Principle (OCP):**
  - Allocation strategy (Greedy heuristic vs Linear Programming / OR-Tools solver) implements a shared `AllocationStrategy` interface, allowing swap without altering route controllers.
- **Liskov Substitution Principle (LSP):**
  - All allocation algorithms respect the same input (Sites list, Depots list) and output contract (`List[Allocation]`).
- **Interface Segregation Principle (ISP):**
  - Replan endpoints return concise IDs for `unchanged: List[int]` rather than redundant full objects to minimize payload bandwidth over degraded command post connections.
- **Dependency Inversion Principle (DIP):**
  - Allocation and replanning logic operate over abstract in-memory models, completely isolated from direct database queries.

## 3. Allocation & Replanning Logic Flow

### Greedy Allocation Loop
1. Query unserved sites: `sites.status NOT IN ('dispatched', 'delivered')`.
2. Compute `priority_score(site, now)` for each site and sort descending.
3. Query available inventory across all depots under the center.
4. For each site (highest priority first):
   - Determine required resources based on site's `needs` and `urgency_flags` (e.g., `pregnancy`/`injury_reported` $\to$ `ambulance`/`boat`; `food` $\to$ 50-100 `food_packet`).
   - Find nearest depot with available matching stock.
   - Allocate requested amounts up to available inventory; decrement temporary available tracker.
   - Attach standardized `reasoning` string generated by `format_reasoning(site)`.
5. Return ranked list of allocations.

### Replanning & Diffing Engine
1. Scope filter: **Strictly query sites where `sites.status NOT IN ('dispatched', 'delivered')`**.
2. Re-run scoring and allocation algorithm against the current snapshot of active inventory and damaged roads.
3. Compare previous ranks vs new ranks:
   - Identify sites whose rank shifted or whose route/depot assignment changed.
   - Compile `changed: List[ReplanChange]` with human-readable reason (e.g., *"Route to Basti Qadirpur blocked via Bridge 7; alternate adds 1.5h. Sultan Kot promoted to Rank 1"*).
   - Compile `unchanged: List[int]` containing only unaffected site IDs.

## 4. API Contract Specifications

### `POST /api/plan/generate`
- **Request (`PlanGenerateRequest`):**
  ```json
  {
    "center_id": 3
  }
  ```
- **Success `200 OK` (`PlanGenerateResponse`):**
  ```json
  {
    "allocations": [
      {
        "site_id": 17,
        "depot_id": 1,
        "rank": 1,
        "priority_score": 245.0,
        "resources": [
          { "resource_type": "boat", "quantity": 1 },
          { "resource_type": "food_packet", "quantity": 50 }
        ],
        "reasoning": "Priority score 245: population 180, flags: elderly_present, pregnancy"
      },
      {
        "site_id": 22,
        "depot_id": 1,
        "rank": 2,
        "priority_score": 190.0,
        "resources": [
          { "resource_type": "boat", "quantity": 1 },
          { "resource_type": "food_packet", "quantity": 80 }
        ],
        "reasoning": "Priority score 190: population 150, flags: water_rising"
      }
    ]
  }
  ```
- **Empty State `200 OK`:** When no unserved sites exist, return `{"allocations": []}`.

### `POST /api/plan/replan`
- **Request (`ReplanRequest`):**
  ```json
  {
    "center_id": 3,
    "trigger": "road_damage"
  }
  ```
- **Success `200 OK` (`ReplanResponse`):**
  ```json
  {
    "changed": [
      {
        "site_id": 22,
        "old_rank": 2,
        "new_rank": 3,
        "reason": "Route blocked by newly submerged Bridge 7, alternate adds 1.5h"
      },
      {
        "site_id": 19,
        "old_rank": 3,
        "new_rank": 2,
        "reason": "Promoted due to unaffected direct road access"
      }
    ],
    "unchanged": [17]
  }
  ```

## 5. Edge Cases & Exception Handling

| Edge Case / Failure Mode | Root Cause | Handling Strategy & Mitigation |
| :--- | :--- | :--- |
| **All depots completely out of resources** | Heavy regional demand exhausted depot stocks. | Return allocations with available resources or empty `resources: []` indicating queued sites awaiting supply restock, with explicit warning note in reasoning. |
| **Zero unserved sites** | All affected sites have completed deliveries. | Return `200 OK` with `allocations: []` (not a 404 or 500 error). Frontend renders clean "All Sites Served" state. |
| **En-route convoy re-assignment attempt** | Replanning triggered while trucks are physically driving. | Filter query strictly enforces `sites.status NOT IN ('dispatched', 'delivered')`. En-route dispatches remain untouched. |
| **Multiple sites with identical priority score** | Tie in population and urgency flags. | Secondary deterministic sort by `site.id ASC` or `distance_km ASC` to ensure stable, non-jittering plan ordering across re-renders. |
| **Invalid Replan Trigger Enum** | Client sends unexpected trigger string. | Pydantic validation restricts `trigger` to `Literal["new_report", "road_damage", "dispatch_complete"]` (returns 422 on invalid). |
